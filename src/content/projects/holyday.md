상대 팀을 저지하며 전장의 석상을 점령해 더 많은 신성력을 얻는 **4인 멀티플레이 AOS 게임**입니다. 2026년 1월부터 5월까지 4인 팀으로 졸업 프로젝트 전시 빌드를 개발했고, PlayX4 상명대학교 부스에서 시연했습니다.

저는 프로그램 실행부터 게임 시작까지의 흐름, UI 레이아웃과 컴포넌트, 게임 규칙을 바꾸는 축복 콘텐츠, Git 및 프로젝트 에셋 관리를 맡았습니다. 축복과 팝업의 초기 구조와 공통 실행 흐름을 주도했으며, 캐릭터 내부 기능과 기도 애니메이션은 담당 팀원과 연결했습니다.

## 데이터와 효과 실행을 분리한 11종의 축복

연못과 상호작용하면 무작위 축복을 얻어 경기 규칙이나 캐릭터의 능력이 바뀝니다. 축복마다 대상과 발동 조건이 달라 한 클래스의 조건문으로 관리하면 기능이 늘수록 수정 범위가 커질 수 있었습니다.

`BlessData`라는 `ScriptableObject`에 타입·등급·현지화 텍스트 같은 정적 데이터를 두고, 실제 효과는 `IBlessLogic` 전략 인터페이스로 분리했습니다. 팩토리 매핑은 축복 타입을 해당 효과의 생성 함수와 연결합니다. 이 구조로 공통 발동 흐름 안에서 11종의 축복을 실행했습니다.

```csharp
public interface IBlessLogic
{
    void Execute(BlessBehaviour self, NetworkObject player);
    void Destroy();
}
```

축복은 **등급을 추첨한 뒤 해당 등급에서 사용 가능한 효과를 선택**합니다. 등급 확률은 Mercy 20%, Grace 50%, HolyMoly 30%이며, 같은 등급 안에서는 가용 축복을 균등 추첨하도록 구현했습니다. 연못에는 `INetworkInteract` 진입점을 두어 멀티플레이 상호작용 흐름에 연결했습니다.

효과 객체는 발동 시 생성해 개별 상태와 정리 책임을 분리했습니다. 캐릭터 스탯이나 직업군 정보가 필요한 효과는 담당 팀원에게 필요한 API와 배경을 전달해 연결했습니다. 객체 생성에 따른 할당은 발생하며, 이 구조의 장점은 효과별 책임과 생성 규칙을 분리하는 데 있습니다.

## 생성부터 해제까지 관리하는 스택 기반 팝업

로비·매칭·인게임·결과 화면에서 팝업이 반복해서 필요했습니다. 각 화면이 프리팹과 리소스 경로를 직접 참조하면 생성·종료 코드가 중복되므로, 호출부에서는 `PopupType` 키만 전달하는 관리자를 구현했습니다.

- `PopupType`과 리소스 주소의 매핑을 한곳에서 관리했습니다.
- Addressables와 UniTask로 팝업을 비동기 생성하고, 표시 직전에 제네릭 초기화 콜백으로 데이터를 전달했습니다.
- `Stack<PopupBase>`로 중첩 순서를 관리하고 최상단부터 닫히도록 했습니다.
- 표시·입력 차단·배경 처리·닫기·이벤트 해제·인스턴스 반환을 공통 흐름에 모았습니다.

```csharp
public async UniTask<PopupBase> Show(string address)
{
    var popup = await InstantiatePopupAsync(address);
    if (popup == null)
        return null;

    if (_popupStack.Count == 0)
    {
        SetActive(true);
        FadeBackground(true).Forget();
    }

    _popupStack.Push(popup);
    await popup.Show();
    return popup;
}
```

닫을 때는 최상단 팝업의 숨김 애니메이션을 실행하고 이벤트를 해제한 뒤 `Addressables.ReleaseInstance()`로 반환합니다. 공유 리소스는 남은 참조 수에 따라 유지됩니다. 이 흐름을 일원화해 화면마다 반복되던 코드와 해제 누락 가능성을 줄였습니다.

## 현지화와 게임 초기화 흐름

AI Agent를 활용해 하드코딩된 UI 텍스트를 현지화 가능한 구조로 전환하고 한국어·영어 선택 기능을 구현했습니다. 축복 데이터도 현지화 문자열을 갖도록 연결했습니다.

게임 필수 매니저는 서비스 로케이터 기반의 공통 접근 지점으로 정리하고, 생성·초기화 순서를 명확하게 만들었습니다. 후반부에는 석상의 공통 상호작용과 UI 표시 계층을 정리해 중복 구현을 줄였습니다. Unity Profiler에서 확인한 매 프레임 컴포넌트 조회는 초기화 시 캐싱하도록 바꾸고, 상태 변경 시에만 갱신할 수 있는 UI는 이벤트 기반으로 전환했습니다. 성능 결과는 이러한 변경 범위로 설명하며, 별도의 전후 측정값은 제시하지 않습니다.

## Git 병합과 팀 협업

기능을 병렬로 개발하면서 PR 병합 충돌이 발생하면 브랜치와 커밋 이력을 추적하고, 관련 팀원과 의도를 확인해 해결했습니다. 개발 후반부에는 팀별로 추가한 코드와 AI 생성 코드의 구조가 맞지 않거나 중복된 부분을 점검하고, 매니저와 UI의 공통 구조로 정리했습니다.

## 결과와 다음에 바꿀 점

팀과 함께 전시 빌드를 완성해 **PlayX4 상명대학교 게임전공 부스에서 현장 시연**을 진행했습니다. 기획 의도와 복잡한 규칙을 안정적으로 구현하는 일이 실제 플레이 경험으로 이어지는 과정을 경험했습니다.

네 명이 여러 역할에 참여하면서 책임과 결정 범위가 충분히 명확하지 않았고, 콘셉트 변경과 코드 규약의 편차가 누적됐습니다. 다음 팀에서는 명명 규칙·폴더 구조·커밋 및 브랜치 규칙을 먼저 문서화하고, 콘텐츠 변경 시 담당자의 검토와 합의를 거치려고 합니다.

주요 로직이 싱글톤과 전체 게임 흐름에 강하게 연결돼 개별 기능을 바로 검증하기 어려웠습니다. 다음에는 기능별 테스트 Scene을 함께 만들어 반복 확인 비용을 줄이고 싶습니다. 멀티플레이 기술도 구현 가능성뿐 아니라 테스트 환경과 운영 비용을 함께 비교해 선택하려고 합니다.

AI 생성 코드 역시 생성 속도와 별개로 구조 검토와 기능 검증이 필요함을 배웠습니다. 공통 아키텍처와 금지 패턴, 검증 절차를 팀 가이드에 담고, 기존 책임 구조에 맞는지 확인한 뒤 병합하는 방식으로 개선하려고 합니다.
