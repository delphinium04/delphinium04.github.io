- 프로그래밍 언어는 **Python**만 사용해야 함
- **Windows** 운영체제에서 실행 가능해야 함
- 이외 별도 엔진 제약 없음 (`Pygame`과 2D 물리 라이브러리 `Pymunk` 채택)

## 2. 팀 구성 및 담당 역할

### 내가 맡은 핵심 구현

- **게임 루프 설계** — `Game.run()`에서 입력 처리, 물리 갱신, 합성 판정, 게임 오버 판정, 화면 출력의 실행 순서를 구성하고 게임 상태(`game_over`, `done`)에 따라 처리 흐름을 분리했습니다.
- **공 합성 조건 판별** — 중첩 반복문으로 공 쌍을 탐색하고, Pymunk가 반환하는 접점의 존재와 동일한 반지름을 합성 조건으로 조합했습니다. 새 공 생성·점수 반영·기존 공 제거를 하나로 묶었으며, 최악 시간 복잡도는 $O(n^2)$입니다.

## 3. 주요 문제와 해결 과정

### 3-1. 게임의 실행 흐름을 프레임 단위로 설계

#### 구현 목표

마감이 가까워졌을 때 팀원들이 작성한 개별 기능들이 서로 연결되지 않아 실행하기 어려운 상태였습니다. 사용자 입력에 따라 공을 생성하고, 물리 이동과 합성 결과를 화면에 반영하는 전체 진행 구조를 설계하여 `Game.run()`의 메인 루프로 통합했습니다.

#### 내가 적용한 방법

한 프레임의 처리 순서를 **입력 처리 → 물리 및 스프라이트 갱신 → 공 합성 판정 → 게임 오버 조건 판정 → 화면 출력**으로 구성했습니다. 물리 상태를 갱신한 뒤 충돌을 검사하고, 합성과 점수 변경이 반영된 상태를 화면에 표시하도록 순서를 정했습니다. 각 단계는 별도 메서드로 나누어 `run()`에서는 게임의 전체 구조를 한눈에 파악할 수 있도록 했습니다.

```python
# Game.run()의 진행 중 처리 부분
self.handle_events()
self.update_physics_and_sprites()
self.merge_colliding_equal_balls()
self.check_ball_touched_boundary()
self.draw()
```

- `game_over` 값에 따라 일반 플레이와 게임 오버 화면 처리를 분기하고, `done` 값으로 반복문의 종료를 제어했습니다.
- 게임 오버 상태에서는 일반 플레이의 물리·합성 처리를 멈추고 재시작이나 종료 입력만 받도록 구성했습니다.
- `clock.tick(60)`으로 초당 프레임 수의 상한을 설정하고, 물리 계산은 매 프레임 `space.step(1/60)`으로 진행했습니다.

#### 구현 결과와 배운 점

입력, 상태 변경, 화면 출력이 매 프레임 반복되면서 실시간 게임이 동작한다는 구조를 직접 완성했습니다. 특히 개별 함수의 기능뿐 아니라 **호출 순서와 상태에 따른 분기**까지 설계해야 게임 전체가 올바르게 맞물린다는 점을 이해했습니다.

### 3-2. 공 쌍 탐색과 접점 정보를 이용한 합성 조건 판별

#### 구현 목표

게임 공간에 존재하는 공 중 합성 가능한 두 공을 찾고, 다음 단계의 공 생성과 점수 반영까지 이어지는 로직을 작성했습니다. 합성 조건은 **두 공 사이에 물리적 접점이 존재하고, 반지름이 같은 경우**로 정의했습니다.

#### 내가 적용한 방법

- `merge_colliding_equal_balls()`에서 중첩 `for`문으로 공 쌍을 탐색했습니다. 두 번째 반복문을 `i + 1`부터 시작해 자기 자신과의 비교를 제외하고, 다른 순서의 같은 쌍을 중복 검사하지 않도록 했습니다.
- 각 쌍을 Pymunk의 `shapes_collide()`로 조회하고, 반환된 `points`가 비어 있지 않으면 접점이 존재한다고 판단했습니다. 이어서 두 공의 반지름(`get_radius()`)이 같은지 확인해 동일한 단계끼리만 합쳐지도록 했습니다.
- 기하학적인 접점 계산은 Pymunk가 담당하며, 비교할 쌍을 탐색하고 접점 존재와 반지름 일치 여부를 조합하는 게임 규칙은 직접 작성했습니다. 이 방식은 충돌 콜백으로 통지를 받는 구조가 아니라, 매 프레임 쌍을 순회하며 접점 정보를 직접 조회하는 구조입니다.

#### 핵심 코드: 합성 조건 판별 (`Suika.py`)

```python
def merge_colliding_equal_balls(self):
    # if ball merged -> return
    for i in range(len(self.balls)):
        for j in range(i + 1, len(self.balls)):
            ball_i, ball_j = self.balls[i], self.balls[j]
            point_set = ball_i.shape.shapes_collide(ball_j.shape)

            is_hit = len(point_set.points) != 0  # 접점 존재 여부
            # hit and level is same
```

#### 합성 이후의 처리

- 조건을 만족하면 두 공의 중심 좌표를 평균 낸 위치에 다음 단계의 공을 생성하고, 공 목록(`self.balls`)과 스프라이트 그룹에 등록한 뒤 점수를 더했습니다.
- 기존 두 공은 공 목록, 스프라이트 그룹, 물리 공간(`space`)에서 모두 제거했습니다.
- 최대 단계의 공끼리 만나는 경우에는 새 공을 생성하지 않고 점수만 더한 뒤 제거했습니다.
- 병합 처리가 끝나면 즉시 `return`하여, 원소가 추가·삭제된 리스트를 기존 인덱스로 계속 순회하지 않도록 막았습니다. 따라서 한 프레임에는 최대 한 쌍이 합쳐지며, 다른 후보는 다음 프레임에서 다시 검사합니다.

#### 시간 복잡도와 한계

공이 `n`개일 때 모든 쌍을 검사하는 경우 비교 횟수는 `n(n - 1) / 2`이므로, 최악 시간 복잡도는 **$O(n^2)$**입니다. 합성 가능한 쌍을 찾으면 일찍 종료하지만, 찾지 못하면 모든 쌍을 검사합니다.

#### 구현 결과와 배운 점

물리 라이브러리가 제공하는 접점 정보를 게임의 합성 규칙에 연결하고, 객체의 생성·제거와 점수 갱신까지 하나의 처리 과정으로 묶었습니다. 이를 통해 **도형 간 기하학적 접점 계산과 게임 규칙에 따른 판정의 역할**을 구분하고, 기능 작성과 별도로 객체 수에 따른 탐색 비용을 검토하는 관점을 배웠습니다.

### 배운 점

Pygame과 Pymunk 같은 외부 라이브러리의 기능을 찾아 게임에 적용하는 방법을 익혔습니다. 공식 문서에서 필요한 API와 사용 조건을 확인하고, Stack Overflow 등 다른 개발자의 사례를 참고하면서 입력 처리, 화면 출력, 물리 객체 관리 방식을 배웠습니다. 특히 예제 코드가 어떤 문제를 해결하는지 파악하고, 내 게임의 구조와 요구사항에 맞게 변형해 적용하는 과정이 중요하다는 것을 체감했습니다.

### 아쉬운 점과 개선 방향

#### 1. 접점 조회와 한 프레임당 한 쌍으로 제한된 합성 처리

현재는 매 프레임 모든 공 쌍의 접점을 직접 조회하며, 한 쌍을 합치면 해당 프레임의 탐색을 종료합니다. 물리 엔진의 접점 정보를 사용하지만 충돌 이벤트에 반응하는 구조가 아니므로, 공의 수가 늘면 검사 비용이 커지고 여러 곳에서 동시에 조건을 만족해도 처리가 다음 프레임으로 나뉩니다.

다시 설계한다면 물리 엔진의 **충돌 콜백(Collision Handler)으로 후보를 모은 뒤, 물리 갱신이 끝난 시점에 서로 겹치지 않는 후보들을 일괄 처리**하고 싶습니다. 한 공이 여러 합성에 중복 사용되지 않도록 관리하면서, 독립적인 쌍들은 같은 프레임에 처리할 수 있도록 개선할 것입니다.

#### 2. 여러 합성 후보 사이의 우선순위 부족

한 공에 같은 단계의 공이 여러 개 붙으면, 현재는 리스트를 순회하면서 먼저 발견한 쌍이 선택됩니다. 위치에 따른 명시적인 우선순위가 없어 플레이어가 어떤 공이 먼저 합쳐질지 예상하기 어렵습니다.

개선한다면 한 공에 여러 후보가 생겼을 때, **상대 공 중 게임 화면 중앙에 더 가까운 공을 우선 선택**하도록 기준을 정하고 싶습니다. 거리가 같은 경우의 동률 처리 순서도 정의해 결과를 일관되게 만들 것입니다.

#### 3. 팀원별 경험 차이를 고려한 역할 분담 부족

팀원 대부분이 1학년으로 Python과 게임 프로그래밍을 막 익혀 가는 단계였고, 구현 경험에도 차이가 있었습니다. 프로젝트 초기에 각자의 숙련도와 학습 속도를 고려해 작업을 나누지 못하면서 핵심 로직과 마무리가 제게 집중되었습니다. 팀 프로젝트였지만 각자가 명확한 역할을 맡아 함께 완성하는 협업 구조를 충분히 만들지 못한 점이 아쉽습니다.

다시 팀 프로젝트를 진행한다면 초기에 각자 수행 가능한 범위를 함께 확인하고, 기능을 작고 구체적인 입출력 단위로 나누어 역할을 정할 것입니다. 짧은 코드 리뷰와 중간 점검을 통해 역할을 조정하면서 팀원 모두가 기여할 수 있는 방식으로 진행하고 싶습니다.
